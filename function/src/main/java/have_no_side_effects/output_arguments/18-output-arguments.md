# Output Arguments## Bản dịch (VI)Các tham số (arguments) thường được hiểu là đầu vào của một hàm. Tuy nhiên, đôi khi chúng lại được dùng như đầu ra. Khi đó, người đọc dễ bị “khựng lại” (double-take) vì không rõ tham số đó là input hay output.Ví dụ:appendFooter(s);Nhìn vào call site, không rõ:- s là cái được thêm vào footer?- hay footer được thêm vào s?Chỉ khi xem chữ ký hàm:public void appendFooter(StringBuffer report)ta mới biết report bị thay đổi. Việc phải nhìn sang phần khai báo hàm để hiểu ý nghĩa của call site là một gián đoạn nhận thức (cognitive break). Clean Code cố gắng loại bỏ những điểm gây gián đoạn như vậy.Trong lập trình hướng đối tượng, hầu hết nhu cầu về output arguments biến mất vì "this" chính là output argument tự nhiên. Thay vì:appendFooter(report);nên viết:report.appendFooter();Như vậy, hành vi thay đổi trạng thái nằm rõ ràng trên chính đối tượng bị thay đổi.Nguyên tắc chung:- Tránh dùng output arguments.- Nếu cần thay đổi trạng thái, hãy để đối tượng tự thay đổi state của nó.- Nếu cần trả kết quả biến đổi, hãy dùng return value thay vì truyền tham số ra ngoài để ghi đè.## Vì sao Output Arguments nguy hiểm?1. Gây double-take tại call site.2. Che giấu side effect.3. Khó test hơn (vì phải kiểm tra object bị mutate).4. Dễ vi phạm Command–Query Separation.## Bad → Good### Badvoid appendFooter(StringBuilder report)### Goodclass Report {void appendFooter() { ... }}Hoặc:String transform(String input)## Checklist- [ ] Hàm có tham số bị mutate không?- [ ] Có thể chuyển thành method của object đó không?- [ ] Có thể return value thay vì mutate tham số không?- [ ] Call site có đọc một lần là hiểu không?## Kết luận cần nắm1. Output argument là một dạng side effect.2. Clean Code ưu tiên hành vi nằm trên chính object sở hữu state.3. Nếu hàm biến đổi dữ liệu → return giá trị mới.4. Nếu hàm thay đổi trạng thái → method của object đó.
